## 摘要
我们提出了多智能体推理与协调（MARC），一个开源框架，用确定性的多智能体编排替代单体式LLM提示，用于临床推理。MARC协调角色专门的智能体进行提取、推理、答案生成和评估，具有显式的上下文传递和可追踪的中间输出，从而实现分阶段失败归因。我们还引入了一个分解器模块，可以从自然语言描述生成任务特定的智能体提示，消除了手动提示工程。该框架支持基于API和本地CPU兼容的部署，并完全通过YAML配置，无需修改代码。MARC设计为模型无关、可解释，并面向没有编程专业知识的临床领域专家可用。完整框架可在https://github.com/Penn-RAIL/MARC-v1获取。

## Abstract
We present Multi-Agent Reasoning and Coordination (MARC), an open-source framework that replaces monolithic LLM prompting with deterministic multi-agent orchestration for clinical reasoning. MARC coordinates role-specialized agents for extraction, reasoning, answer generation, and evaluation, with explicit context passing and traceable intermediate outputs, enabling stage-wise failure attribution. We additionally introduce a Decomposer module that generates task-specific agent prompts from a plain-language description, eliminating manual prompt engineering. The framework supports both API-based and local CPU-compatible deployments and is entirely configurable via YAML, without code modifications. MARC is designed to be model-agnostic, interpretable, and accessible to clinical domain experts without programming expertise. The full framework is available at https://github.com/Penn-RAIL/MARC-v1.

- **背景**：大语言模型（LLM）在医学领域已展现出广泛应用潜力，包括自动报告生成、临床问答、医学影像解释等。例如 GPT-5、Med-PaLM 2 在医学问答基准上表现优异，MedGemma 等模型进一步扩展到影像-文本推理。然而，这些系统在临床部署中仍面临**可靠性、透明性和安全性**的关键挑战。
- **核心问题**：绝大多数临床 LLM 系统仍依赖**单体提示（single-prompt）策略**——即一个 LLM 实例同时承担提取、推理、验证和动作生成等所有任务。这种“一锅端”的方式存在三重缺陷：
  - **可解释性差**：当系统输出错误结果时，无法判断错误源于信息提取遗漏、推理缺陷、指令遵循失败还是格式问题——所有失败模式都隐藏在单个不透明的响应中。
  - **上下文整合不足**：放射学等临床决策往往需要综合多个信息源、经过多步推理才能得出，单体提示难以支持这种迭代式推理。
  - **提示工程门槛高**：手动设计高质量提示需要大量专业技术经验，阻碍了临床领域专家直接参与系统构建与优化。
- **整体含义**：MARC 旨在用**确定性多智能体编排**替代单体提示，将临床推理拆解为可追踪、可归因、可配置的阶段，使临床 AI 系统具备可解释性、可调试性和机构可部署性。

## 论文提出的方法论

### 核心思想
MARC 采用**角色专门化（role specialization）**的多智能体架构：每个智能体只负责一个明确子任务，通过显式上下文传递串联成完整管道，实现“提取 → 推理 → 生成”的职责分离。该方法借鉴软件工程的可配置理念，将编排逻辑、模型选择、提示设计与执行代码彻底解耦。

### 关键技术细节
- **多智能体设计**：采用**二级自主性（Level 2 autonomy）**的结构化工作流模式，即智能体按预定顺序执行、阶段间显式交接。与固定管道方法（如 RadFabric）不同，MARC 通过 **YAML 配置文件**定义智能体序列、模型分配和知识增强方式，用户无需修改代码即可调整整个管道。
- **Decomposer 模块**：这是论文的重要创新之一。给定自然语言任务描述，Decomposer 使用 **MedGemma 4B** 在单轮对话中完成任务解析，自动生成三个子任务的角色专属提示模板，输出结构化 JSON 规范（含智能体名称、角色和完整提示）。生成的提示会经过结构约束校验（变量绑定正确性、VERDICT 格式约定、输出长度限制），然后写入磁盘并加载到 MARC 管道中。
- **Agent 提示策略**：所有智能体在 **temperature = 0**、零样本条件下运行，保证输出完全确定可复现。每个提示模板包含四个组件：角色定义、显式任务指令、输出约束、运行时变量。
- **三智能体默认管道**：
  - **Agent 1（信息提取）**：接收原始临床输入，提取 2-4 条任务相关证据要点，明确禁止给出结论。
  - **Agent 2（分类与分析）**：接收原始输入 + Agent 1 的证据，进行结构化多步推理，以标准化 VERDICT 行（如 `VERDICT = <label>` 或 `FINAL = yes/no/maybe`）结尾。
  - **Agent 3（推荐生成）**：定位并原样返回 VERDICT 行，不附加任何解释。
- **上下文传递机制**：支持两个运行时变量——`{input}`（原始用户查询）和 `{previous_agent_output}`（前序智能体的结构化输出）。这种显式绑定防止智能体“幻觉”缺失上下文，保证阶段间信息边界清晰。所有中间输出均被记录，支持**阶段级失败归因**。
- **可扩展架构**：默认管道可扩展为包含条件路由的放射学工作流——正常报告可绕过分类/随访环节直达评估器。
- **部署模式**：
  - **API 模式**：使用 Google Gemini 模型家族（gemini-2.0-flash, gemini-1.5-flash），通过 Google AI Studio 配置 API 密钥即可。
  - **本地模式**：通过 Ollama 实现 CPU 兼容推理，适合无法将受保护健康信息发送至外部 API 的机构环境。

## 论文的主要结论与发现

1. **多智能体编排可提升临床推理可解释性**：通过将认知步骤分离到专门智能体并记录中间输出，MARC 实现了“在管道哪个环节出错”的定位能力，这是单体提示无法提供的。
2. **配置化设计显著降低使用门槛**：YAML 外部化配置使临床研究者无需编程即可修改模型、提示与知识源，Decomposer 进一步消除了手动提示工程的需要。
3. **双模式部署适应机构约束**：同时支持外部 API 和本地 CPU 推理，兼顾了性能灵活性（API 大模型）与数据管控（本地小模型）两方面的需求。
4. **模型无关架构适应快速演进**：每个智能体可独立分配不同模型，允许根据成本、延迟、隐私或领域专长逐阶段优化。
