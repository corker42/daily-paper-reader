## 摘要
LLM智能体越来越多地被构建用于医疗工作，并在临床基准上评分。然而，每个这样的分数都来自在智能体执行框架内运行的模型，该框架控制系统在模型与其环境之间的循环。因此，智能体的分数是模型—框架对的属性。对于医疗智能体，结果随框架变化有多大，鲜有测量。测量这种变化并解释它带来两个挑战。第一，框架比较必须除框架外不改变任何东西，并在不同模型和任务类型上重复。第二，比较整个框架会将其机制捆绑在一起，因此无法表明单个机制何时有帮助。为应对这些挑战，我们提出MedicalHarness，一项关于模型和智能体执行框架在医疗任务上的受控研究。我们首先构建MedicalHarnessBench，在四个领域中的107个任务上评估智能体，每个领域测试不同的框架能力。使用该基准，我们在五种智能体执行框架下运行五个开放权重模型，在比较中仅改变框架，并分析结果和执行轨迹。为研究单个机制，我们构建MH-Lab，一个受控框架，在共享执行循环中一次关闭上下文管理、规划或工具暴露中的一项。我们发现，框架及其与模型的交互解释了约四分之一的结果方差，并且没有单一框架在所有模型和任务上都是最佳的。代码和数据见 https://github.com/REAL-Lab-NU/MedicalHarness。

## Abstract
LLM agents are increasingly built for medical work and scored on clinical benchmarks. Each such score, however, comes from a model running inside an agent harness, the system that controls the loop between the model and its environment. An agent's score is therefore a property of a model--harness pair. For medical agents, how much outcomes change with the harness has rarely been measured. Measuring this change, and explaining it, raises two challenges. First, a harness comparison must change nothing but the harness and be repeated across models and kinds of task. Second, comparing whole harnesses leaves their mechanisms bundled together, so it cannot show when an individual mechanism helps. To address these challenges, we present MedicalHarness, a controlled study of models and agent harnesses on medical tasks. We first build MedicalHarnessBench to evaluate agents on $107$ tasks across four domains that each test a different harness capability. Using this benchmark, we run five open-weight models under five agent harnesses, changing only the harness within a comparison, and analyze both outcomes and execution traces. To study individual mechanisms, we build MH-Lab, a controlled harness that switches off context management, planning or tool exposure one at a time within a shared execution loop. We find that the harness and its interaction with the model account for about a quarter of the outcome variance, and that no single harness is best across models and tasks. Code and data are available at https://github.com/REAL-Lab-NU/MedicalHarness.

## 一、核心问题与研究动机

- **核心问题**：医疗 LLM 智能体的基准分数并非仅由模型决定，而是由“模型—执行框架（harness）”这一组合共同决定。harness 控制模型看到什么、能调用哪些工具、动作如何执行、历史如何管理、何时终止。因此，智能体得分本质上是 **model–harness pair** 的属性。
- **研究缺口**：在医疗领域，harness 对结果的影响有多大、为什么有影响，缺乏受控测量。已有医疗基准（MedAgentBench、AgentClinic、HealthAgentBench、MedMemoryBench 等）主要衡量“智能体能做什么”，而非“框架改变了多少”。
- **两大挑战**：
  - **挑战 1**：框架比较必须只改框架，固定模型、服务条件、预算，并跨模型、跨任务类型重复；否则分数差异会混合模型、服务、预算等混杂因素。
  - **挑战 2**：整包比较 harness 会把上下文管理、规划、工具暴露等机制捆绑在一起，无法判断单个机制何时有用；且某些机制只在特定条件下才会“触发”。
- **整体含义**：论文主张将医疗智能体评测从“只看模型”推进到“模型—harness 联合评估”，并呼吁报告模型—框架对及答案率等诊断指标。

## 二、方法论

- **核心思想**：构建受控基准与受控实验框架，分别回答“harness 影响多大”和“哪个机制在何时起作用”。
- **harness 的形式化定义**：harness 是一个三元组 \(h=(C_h,U_h,T_h)\)，在任务初始状态 \(s_0\) 上循环：
  - \(c_t=C_h(s_t)\)：构造模型上下文（指令、工具描述、历史）；
  - \(a_t\sim\pi_m(\cdot|c_t)\)：模型生成动作；
  - \((o_t,s_{t+1})\sim U_h(\cdot|s_t,a_t;x)\)：执行动作、收集观测、更新状态（含工具路由、输出检查、摘要等辅助模型调用）；
  - \(T_h(s_t)\)：决定何时停止。
  - 智能体为 \((m,h)\)，轨迹由 oracle 评分 \(Y=R_x(\tau)\in[0,1]\)。
- **模型—harness 方差分解**：对平衡设计（模型 \(m\)×harness \(h\)×种子 \(\sigma\)）：
  - \(\bar{y}_{mh\sigma}=\mu+\alpha_m+\beta_h+\gamma_{mh}+\varepsilon_{mh\sigma}\)
  - \(SS_T=SS_M+SS_H+SS_{MH}+SS_E\)
  - **harness share** \(=(SS_H+SS_{MH})/SS_T\)，衡量 harness 及其与模型交互的贡献。
- **harness 方差 vs 模型方差**：\(HV(m)=\mathrm{Var}_h(\bar{y}_{mh\cdot})\)，\(MV(h)=\mathrm{Var}_m(\bar{y}_{mh\cdot})\)；在平衡设计中 \(HV>MV\) 当且仅当 \(SS_H>SS_M\)。
- **MedicalHarnessBench**：107 个可执行医疗任务，四个能力域：
  - **MedTool**（32 题，临床计算）：从 SQLite 病历中识别计算器并取数、处理依赖与分支，输出 2–10 个结果。
  - **MedMemory**（23 题，长上下文检索）：70–100 段会话历史，证据常在数十段之前，输出简短事实答案。
  - **MedPlanning**（28 题，临床数据工作流）：试验资格筛选、EHR 处理、全切片图像肿瘤定位等，输出结构化文件。
  - **MedWeb**（24 题，浏览器交互）：EMR、支付方门户、传真门户间导航并更新应用状态。
- **MH-Lab**：基于 LangGraph 的 ReAct 式共享执行循环，含三个可独立关闭的开关：
  - **上下文管理**：当估计输入达预算 80% 时，同一模型对旧历史做摘要；关闭则保留完整历史。
  - **规划**：提供 `update_plan` 工具、规划指令、提醒并每轮展示计划；关闭则全部移除。
  - **工具暴露**：任务工具直接给出名称、描述、参数 schema；关闭后须经 `tool_search`、`tool_describe`、`tool_call` 发现后调用。
- **评分**：MedTool 为“计算器选择 F1 × 正确输出比例”；其余三域为二元结果（MedMemory 别名匹配、MedPlanning 任务自带检查、MedWeb 全部最终状态检查通过）。过程诊断包括选择 F1、参考集召回、过程检查通过率，MedMemory 用 LLM judge 评工具使用、证据一致性、故障恢复。

## 三、实验设计

- **数据集/场景**：MedicalHarnessBench 的 107 个任务，源自 MedMCP-Calc（MIT）、MedMemoryBench（Apache-2.0）、HealthAgentBench（MIT）、HealthAdminBench（Apache-2.0）；上游 2,293 个任务经自动筛选、外部模型审核与人类专家复核后保留 107 个。
- **模型**：五个开放权重模型，26B–120B：Gemma4-26B-A4B、Qwen3.6-35B-A3B、GPT-OSS-120B、Nemotron-3.5-30B-A3B、GLM-4.7-Flash；由 vLLM 本地服务，统一 checkpoint 与上下文窗口。
- **harness**：OpenClaw、Hermes、ZeroClaw、Codex CLI、Claude Code，均通过自定义 provider 接口接入本地模型；除少量为完成任务所需的默认值修改外，保留各自发布设置。
- **主实验协议**：每个模型—harness 对跑全部 107 任务 × 种子 42/43/44，共 **8,025 episodes**；每 episode 一小时墙钟限制，独立沙箱，隐藏评分器与金标准。
- **机制实验（MH-Lab）**：Qwen3.6-35B-A3B 与 GPT-OSS-120B，在四个环境、三种“一次关闭一个机制”条件下共 **2,568 scheduled episodes**，输入预算 65,536 tokens。
- **对比对象**：同模型下不同 harness 的横向对比（只变 harness）；MH-Lab 中 full 与 −context management、−planning、−tool exposure 的配对对比；另在真实产品 harness 上做模块开关（如 ZeroClaw 的 submission check、Hermes 的 tool search）作为外部验证。
- **指标**：outcome、过程诊断（Proc.）、答案率（answer rate）、每 episode 百万 token 消耗（MTok）、执行轨迹统计（溢出、轮数、超时、被拒调用等）；配对 bootstrap 给出 95% 区间。

## 五、实验数量与充分性

- **实验规模**：
  - 主矩阵：5 模型 × 5 harness × 107 任务 × 3 种子 = 8,025 episodes。
  - 机制矩阵：2 模型 × 4 条件 × 107 任务 × 3 种子 = 2,568 scheduled episodes。

- **充分与公平之处**：
  - 同一比较内只改变 harness，模型 checkpoint、服务栈、上下文窗口、episode 截止时间、种子集固定。
  - 跨 5 个模型、4 类任务、3 个种子重复，并用配对 bootstrap 处理任务抽样不确定性。

- **不足与限制**：
  - 部分环境任务量小（MedPlanning 28、MedWeb 24、MedMemory 23），排名不确定性大：20 个模型—环境对中仅 2 对的领先者优势 95% 区间排除零。

  - 种子间 run-to-run 方差平均 18%，MedPlanning 高达约 40%，说明部分结论受随机性影响较大。
  - 仅评估开放权重模型，未覆盖前沿闭源模型；harness 版本与配置随时间变化，结果可能不可直接迁移。

## 六、主要结论与发现

- **方差分解**：四环境平均，模型解释 **58%**，harness **12%**，模型×harness 交互 **12%**，种子间运行波动 **18%**；即 harness 及其交互合计约 **四分之一**。
- **方向性比较**：总体上改变模型比改变 harness 更能移动分数（HV/MV 在 MedTool 0.18、MedMemory 0.64、MedPlanning 0.47、MedWeb 0.23）；仅在三主模型的 MedMemory 上 HV/MV = 1.45，harness 主效应超过模型。
- **无单一最优 harness**：领先者随模型和环境变化；MedTool 上 Hermes 领先三个模型，Claude Code 领先 GPT-OSS-120B，Codex 领先 Nemotron。
- **答案率 vs 得分**：在 MedTool 和 MedMemory 上，10 个模型—环境对中 9 个的 harness 间差异更多体现在“是否给出答案”而非“已答题目得分”；共享题目上得分差异仅 0.02–0.06，答案率差异可达 0.54。
- **各环境难点**：MedTool 计算器选择 F1 约为数值准确率两倍（选对不等于算对）；MedMemory 证据越远准确率越低；MedPlanning 试验筛选平均返回 13.6–33.7 个试验而合格仅 4.8 个；MedWeb 各 harness 下不足一半 episode 通过全部检查。
- **机制结论**：
  - **上下文管理**决定长轨迹能否存活：关闭后 MedWeb 输入溢出至 67/72（Qwen）与 48/65（GPT-OSS），结果分别下降 0.39 与 0.17；MedPlanning 参考集召回下降 0.29 与 0.16。
  - **规划**帮助部分模型维持长流程：GPT-OSS-120B 在 MedWeb 中位轮数从 176.5 降至 63，结果与过程分下降 0.18/0.19；Qwen 在 MedTool 上未完成输出从 24 增至 47、超时翻倍。
  - **工具暴露**接口须匹配模型调用习惯：工具藏在搜索后，模型仍直接按名调用而被拒（Qwen 95/96、GPT-OSS 86/96 的 MedTool episode），Qwen 花费约 3 倍 token 而结果不变，GPT-OSS 四环境均下降。
  - 产品 harness 验证：ZeroClaw 的提交检查把 Qwen 的 MedMemory 从 0.42 提升到 0.51；Hermes 关闭 tool search 后 Qwen 在 12 个 MedWeb 任务上从 0.17 升至 0.50。

## 七、优点

- **受控设计严格**：比较中只改变 harness，固定模型、服务栈、预算与种子，并以 8,025 episodes 的规模跨模型、跨任务重复。
- **方差分解方法清晰**：将总分方差拆为模型、harness、交互、运行噪声四部分，并给出 HV/MV 的可证明比较，量化了“harness 有多重要”。
- **机制解耦实验**：MH-Lab 在共享循环中一次只关闭一个机制，弥补了整包 harness 比较无法定位机制的缺陷。
- **诊断维度丰富**：除 outcome 外报告答案率、过程分、token 消耗、溢出、超时、被拒调用等，能区分失败类型。
- **可复现与开放**：公开代码与数据；对 harness 版本、默认值改动、服务设置、隔离与统计方法均有详细记录。
- **实践导向**：给出“保留临床证据、将计划锚定临床标准、验证任务完成”等设计建议，并发现“隐藏工具反而增加 token/降低准确率”等反直觉现象。

## 八、不足与局限

- **算力信息缺失**：未报告 GPU 型号、数量与推理总时长，成本不可复现量化。
- **模型覆盖有限**：仅 5 个开放权重模型（26B–120B），无前沿闭源模型；结论对更大/更强模型的外推性未知。
- **任务规模偏小**：单环境 23–32 题，排名不稳定；多数领先者优势不显著，个别显著结论仅对单一模型成立。
- **机制实验的外部效度**：MH-Lab 通过降低输入预算强制摘要触发，与原生产品 harness 中摘要仅 2–5% 触发率的实际场景不同；原生设置下无法检测该机制。
- **随机性影响**：种子间方差平均 18%，MedPlanning 约 40%，部分环境（尤其成功极少的任务）结论可能被噪声主导。
- **评估范围限制**：过程分部分依赖 LLM judge（gpt-4o-mini）评 MedMemory；未涉及真实临床部署中的隐私、安全、监管、人机协作与成本效益。
- **版本与配置敏感性**：harness 版本、默认值修改、上下文窗口、输出上限等设置会影响结果，结论可能随时间与配置漂移。
- **偏差风险**：任务经上游筛选与人类专家复核，可能存在选择偏差；仅使用开放权重模型与本地服务

，且本地 vLLM 服务、统一 checkpoint、固定上下文窗口等工程选择虽增强了内部效度，却可能削弱对闭源 API 模型、异构临床 IT 系统、多语言与跨机构场景的外推能力。此外，评分器与 LLM judge 的判定偏好、任务构造者对“正确临床行为”的隐含假设，也可能系统性地影响某些 harness 的表现，使结论带有一定构造者偏差。

## 九、总体评价与启示

- **方法论贡献**：论文把智能体评测的基本单位从“模型”推进为“模型—harness 对”，并通过方差分解将 harness 主效应、模型×harness 交互与运行噪声分离，使“框架有多重要”从经验判断变为可量化问题。
- **实践启示**：医疗智能体选型不应只比较模型榜单，而应联合调优模型与 harness。长程任务优先保障上下文管理；规划机制对部分模型和长流程有明显价值，但并非普遍增益；工具暴露方式必须匹配模型的调用习惯，盲目隐藏工具可能增加 token 成本并降低成功率。
- **基准建设启示**：未来医疗智能体基准应报告模型—harness 对、答案率、条件准确率、过程诊断与运行方差，并扩大单环境任务量、预注册机制开关、明确机制触发条件，以降低排名不稳定与外部效度不足的问题。
- **临床转化边界**：当前证据仍属于离线、可执行任务层面的基准评估，不能直接证明临床安全、有效或可部署。真实临床落地还需补充隐私保护、越权操作、监管合规、人机协作、成本效益与前瞻性外部验证。
- **总体结论**：harness 是医疗 LLM 智能体性能的重要但非唯一决定因素；约四分之一方差可归因于 harness 及其与模型的交互。不存在跨模型、跨环境通用的最优 harness，更稳健的路径是围绕具体模型、任务与临床工作流进行联合评估、机制诊断与持续验证。
